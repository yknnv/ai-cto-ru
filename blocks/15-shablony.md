# Блок 15. Шаблоны и приложения

Здесь собраны рабочие документы, на которые ссылается курс. Каждый шаблон служит отправной точкой, поэтому подстраивайте его под свою компанию: готового ответа в нём нет. Это приложение будет дополняться.

Все шаблоны и промпты курса собраны в репозитории-шаблоне [ai-cto-starter](https://github.com/yknnv/ai-cto-starter). Его можно взять за основу своего проекта: там уже лежат файл контекста, документы внедрения, шаблон спецификации и промпты. Набор сделан под Claude Code, но подходит и для других агентов.

## Модель окупаемости

Это структура расчёта на квартал, заполняйте её своими числами. Подробный пример на команде из 10 инженеров с токенами, подписками и дефектами разобран в [блоке 04](04-stoimost-tokenov-okupaemost.md), здесь только форма и заполненный образец.

| Строка | Как считать | Образец (10 инженеров, квартал) | Ваши числа |
| --- | --- | --- | --- |
| Р1. Подписки | инженеры × цена × 3 | 10 × 40 $ × 3 = 1 200 $ |  |
| Р2. Токены по API | для плана – ориентир (инженеры × 200 $ × 3), для отчёта – факт за квартал из данных инструмента | 10 × 200 $ × 3 = 6 000 $ |  |
| Р3. Своё железо | амортизация + люди, квартал | 0 (нет) |  |
| Р4. Платформенная работа | доля ставки × месяцы × месячная стоимость ставки | 25% × 3 × 5 000 $ = 3 750 $ |  |
| Р5. Обучение | инженеры × часы × стоимость часа | 10 × 8 × 30 $ = 2 400 $ |  |
| **Р. Итого расходы** | Р1 + Р2 + Р3 + Р4 + Р5 | **13 350 $** |  |
| Э1. Единиц поставки до | baseline, деплои за квартал | 50 |  |
| Э2. Единиц поставки после | факт за квартал пилота; если пилот короче квартала, пересчитайте на квартал | 60 |  |
| Э3. Расходы на команду до | люди + инфраструктура, без ИИ | 150 000 $ |  |
| Э4. Стоимость единицы до | Э3 / Э1 | 3 000 $ |  |
| Э5. Стоимость единицы после | (Э3 + Р) / Э2 | 163 350 / 60 = 2 722,5 $ |  |
| Э6. Экономия на поставке | (Э4 − Э5) × Э2; расходы на ИИ уже внутри Э5 | 277,5 × 60 = 16 650 $ |  |
| Э7. Дефектов на проде до / после | баг-трекер | 8 / 9 |  |
| Э8. Стоимость дефекта | часы разбора и исправления × ставка | 3 000 $ |  |
| Э9. Поправка на дефекты | (до − после) × Э8 | (8 − 9) × 3 000 = −3 000 $ |  |
| **И. Итог за квартал** | Э6 + Э9; Р второй раз не вычитаем | 16 650 − 3 000 = **13 650 $** (около 1,17 млн ₽ по курсу ЦБ на 9 октября 2026) |  |

Если И отрицательный через квартал, это нормально; через 2 квартала – повод пересмотреть подход. В веб-версии курса эта таблица интерактивная: заполняются только входные строки (Р1–Р5, Э1–Э3, Э7, Э8), остальные считаются сами.

**Расходы:** лицензии и подписки (число инженеров × цена); токены по API (для плана – ориентир, для отчёта – фактический расход за период); своё железо, если есть (амортизация оборудования + люди на обслуживание, в пересчёте на квартал); платформенная команда (доля ставки × месяцы × месячная стоимость ставки); обучение (часы инженеров × стоимость часа). Всё вместе даёт итог расходов.

**Эффект:** число единиц поставки за квартал до внедрения (baseline) и после него. Стоимость единицы поставки считается так: все расходы на разработку, включая расходы на ИИ, делятся на число единиц. Разница в стоимости единицы × число единиц = экономия или перерасход за квартал. Отдельно считается изменение числа дефектов на проде × средняя стоимость дефекта.

**Итог:** экономия на поставке плюс поправка на дефекты. Расходы на ИИ уже вошли в стоимость единицы после, второй раз их не вычитают. Отрицательный результат через квартал считается нормальным, а через 2 квартала это уже повод пересмотреть подход.

## Файл контекста для репозитория

Это файл в корне репозитория, который ассистент или агент читает перед работой. У разных инструментов он называется по-разному (CLAUDE.md, AGENTS.md, .cursorrules), но содержание одинаковое.

```
# О проекте
Что это за система, для кого она и какую бизнес-задачу решает. 2 или 3 предложения.

# Архитектура
Основные модули и за что они отвечают. Как они связаны. Где точки входа.

# Договорённости
Принятые и запрещённые библиотеки. Формат логов. Обработка ошибок.
Правила именования и список того, что считается публичным интерфейсом и не меняется без согласования.

# Как проверять
Команда для запуска тестов. Команда для линтера. Что должно проходить до пул-реквеста.

# Чего не делать
Модули, которые нельзя трогать. Операции, для которых нужно подтверждение человека.
Данные, которые нельзя использовать в примерах.

# Типичные задачи
2 или 3 примера того, как здесь принято делать типовые вещи, со ссылками на образцовый код.
```

Файл должен быть коротким: модель читает его каждый раз, поэтому длинный файл дорого стоит ([блок 04](04-stoimost-tokenov-okupaemost.md)) и хуже работает.

Так выглядит заполненный файл для пилотного сервиса Даниила – около 40 строк, и это нормальный размер:

```
# О проекте
fees-service считает комиссии за переводы и операции по картам для розничных клиентов.
Вызывается синхронно из transfers-service и cards-service, ответ нужен за 50 мс (p95).
Ошибка в расчёте – это претензия клиента и отчёт регулятору, поэтому точность важнее скорости разработки.

# Архитектура
- api/        REST-контроллеры, точка входа FeeController
- core/       правила расчёта, класс FeeCalculator – сердце системы
- tariffs/    загрузка тарифов из справочника, кеш на 15 минут
- persistence/ JPA-репозитории, схема в db/migrations (Flyway)
- reporting/  выгрузки для регулятора, не трогать без согласования

# Договорённости
- Java 17, Spring Boot 3. Новые зависимости только из внутреннего реестра (см. allowed-deps.txt).
- Деньги – только BigDecimal, округление HALF_EVEN, никогда double.
- Логи в JSON через общий логгер, без номеров карт и счетов (только маскированные).
- Ошибки – исключения из core/errors, коды из errors.yaml.
- Публичный интерфейс: всё в api/ и схема базы. Меняется только через спецификацию.

# Как проверять
- ./gradlew test          – модульные, должны проходить всегда
- ./gradlew integration   – интеграционные, нужен Docker
- ./gradlew lint          – линтер по стандартам банка
До пул-реквеста: тесты и линтер зелёные, покрытие изменённых строк не ниже 70%.

# Чего не делать
- Не менять core/FeeCalculator и reporting/ без спецификации и ревью 2 сеньоров.
- Не добавлять миграции схемы без подтверждения человека.
- Не использовать реальные данные клиентов в тестах, только генератор fixtures/.
- Не запускать команды деплоя и не трогать файлы в deploy/.

# Порог спецификации
Через спецификацию (specs/): изменение api/, схемы базы, core/, больше одного модуля.
Без спецификации: исправление ошибки в одном модуле, тексты, тесты, рефакторинг внутри модуля.

# Типичные задачи
- Новое правило комиссии: по образцу core/rules/CrossBorderFeeRule.java, тест рядом.
- Новый код ошибки: добавить в errors.yaml, затем в core/errors, см. коммит a81f2c.
- Документация модуля: формат docs/MODULE_TEMPLATE.md.
```

Правила ИБ в этом файле не прописаны намеренно: они лежат в отдельном policies.md, пример которого есть в [блоке 05](05-bezopasnost-politika-ii.md).

Из опыта со своим инструментом из [блока 03](03-ii-agenty-i-podhody.md) я вынес 2 правила, которые касаются любого файла контекста. Первое правило: держите в разных файлах сгенерированное из кода и написанное людьми (правила ИБ, архитектурные ограничения). Если они лежат вместе, одна перегенерация молча удалит правило безопасности и оставит после себя правдоподобный документ. Второе правило: если хотите, чтобы работа через спецификацию была правилом по умолчанию, запишите в файл контекста порог. Порог говорит, что идёт через спецификацию (изменение публичного контракта, схемы базы, больше одного модуля) и что идёт без неё (исправление ошибки, правка текста, рефакторинг внутри модуля). Правило без порога срабатывает на исправлении опечатки, поэтому через неделю его отключают.

Готовые шаблоны спецификации, проектирования и задач для существующего кода лежат в репозитории этого инструмента (ссылка в [блоке 03](03-ii-agenty-i-podhody.md)), в папке templates. Там же есть профиль правил по 152-ФЗ в формате «триггер, требование, что должно быть в спецификации», который можно взять как образец для своих регуляторных правил.

Скопируйте промпт в модель, которую разрешила ваша служба ИБ (ChatGPT, Claude, GigaChat, YandexGPT или другую). Модель задаст вопросы по одному и по ответам соберёт документ. Не вставляйте в ответы секреты, персональные данные и код из закрытых систем.

```
Не проси вставлять код: мне достаточно назвать модули, команды и пути к файлам. Пиши коротко. ## Шаблон спецификации для ИИ
```

```
Бизнес-причина: что изменится для пользователя или системы.

Конкретное описание результата, без слов «улучшить» и «оптимизировать».

Ниже – второй пример, короче и из другой среды: продуктовая компания Марии, выгрузка заказов в CSV (табличный файл, где значения разделены запятыми). Задача на один день, но спецификация всё равно нужна, потому что затрагивает публичный контракт.

```

```
## Зачем
Клиенты тарифа «Бизнес» выгружают заказы в бухгалтерию вручную, копируя таблицу. 5 обращений в поддержку за месяц, 2 клиента назвали это причиной ухода.

## Что сделать
Кнопка «Экспорт в CSV» на странице /orders с учётом текущих фильтров. Файл формируется синхронно при объёме до 10 000 строк, при большем – отправляется ссылкой на почту в течение 10 минут.

## Где
frontend: pages/orders/Toolbar.tsx; backend: api/orders/export.py (новый), общий модуль exports/ для фоновой генерации уже есть.

## Ограничения
Кодировка UTF-8 с BOM (иначе Excel на Windows покажет нечитаемые символы). Разделитель – точка с запятой, как в остальных выгрузках. Суммы – с 2 знаками, разделитель дробной части – запятая. Не больше 1 экспорта в минуту на пользователя.

## Критерии приёмки
1. Экспорт 9 999 строк отдаёт файл сразу, 10 001 – письмо со ссылкой, ссылка живёт 24 часа.
2. Фильтры страницы (период, статус, менеджер) применяются к выгрузке.
3. Файл открывается в Excel и в Google Sheets без ручного выбора кодировки.
4. Второй запрос в течение минуты получает 429 и понятный текст.
5. Поля: номер, дата, клиент, сумма, статус, менеджер – в этом порядке, заголовки на русском.

## Чего не делать
Не добавлять форматы XLSX и PDF (отдельная задача). Не менять существующие выгрузки в exports/. Не хранить файлы дольше 24 часов.

## Открытые вопросы
Нужно ли включать отменённые заказы по умолчанию? (К продукту, ответ до старта.)
```

## Политика использования ИИ

Политика занимает 1 страницу и имеет такую структуру:

1. **Разрешённые инструменты:** список с названиями и тарифами. Всё остальное запрещено, а новый инструмент добавляется по заявке такому-то.
2. **Аккаунты:** только корпоративные. Личные аккаунты для рабочего кода запрещены.
3. **Что нельзя отправлять в модель:** секреты и ключи, персональные данные клиентов, код систем из списка (перечислить), внутренние документы с грифом.
4. **Ответственность:** за код отвечает тот, кто его смержил. Ссылка на ИИ как источник ответственности не снимает.
5. **Ревью:** код с участием ИИ проходит те же проверки, что и любой другой. Автор должен уметь объяснить, что делает код.
6. **Агенты и бюджет:** действия с внешней отправкой данных, удалением и деплоем требуют подтверждения человека. Лимит на расход токенов: при каком уровне уведомление и при каком остановка.
7. **Журнал и инциденты:** все запросы к модели пишутся в журнал с привязкой к сотруднику, журнал хранится у нас. Если отправили лишнее, нужно сообщить такому-то в течение такого-то срока. За своевременное сообщение санкций нет.
8. **Контакты:** к кому идти с вопросами.

Так эта структура выглядит заполненной. Это политика банка Даниила на первый квартал пилота: 1 страница для инженеров, согласована с ИБ и юристами. Приложения для юристов со ссылками на положения Банка России входят в тот же документ, а уточнения проекта из [блока 05](05-bezopasnost-politika-ii.md) лежат отдельным файлом в репозитории.

```
ПОЛИТИКА ИСПОЛЬЗОВАНИЯ ИИ В РАЗРАБОТКЕ – версия 1.0, действует с 01.11.2026, владелец: технический директор, согласовано: ИБ, Юридический департамент

1. Разрешённые инструменты
   - Агент в IDE «<название>» корпоративной версии, модель отечественного поставщика по договору, данные хранятся и обрабатываются в России.
   - Чат-ассистент на той же модели по адресу ai.internal.
   Всё остальное запрещено. Новый инструмент добавляется заявкой в ИБ через форму SEC-AI-REQ; срок рассмотрения – 10 рабочих дней.

2. Аккаунты
   Только корпоративная учётная запись через единый вход. Личные аккаунты внешних сервисов для рабочего кода запрещены, в том числе с личных устройств.

3. Что нельзя отправлять в модель
   Секреты, ключи, токены, пароли; персональные данные клиентов и сотрудников; исходный код систем из перечня критичных (ledger, reporting, antifraud) целиком – допускаются фрагменты до 200 строк без конфигураций; документы с грифом «Для служебного пользования» и выше.

4. Ответственность
   За код отвечает тот, кто его смержил. Ссылка «это написала модель» ответственности не снимает. Автор пул-реквеста должен уметь объяснить каждое изменение.

5. Ревью и проверки
   Код с участием ИИ проходит те же проверки конвейера, что и любой другой (блок 09). В описании пул-реквеста обязательна отметка «ИИ: да/нет» и ссылка на спецификацию, если она требовалась по порогу из файла контекста.

6. Агенты и бюджет
   Действия агента с деплоем, удалением данных, отправкой данных за контур, изменением прав доступа и миграциями схемы выполняются только после подтверждения человека. Агент не имеет учётных данных продуктивных сред. Лимит на расход токенов задаётся на команду: при 70% – уведомление лиду, при 100% – остановка агентных запусков до решения технического директора.

7. Журнал и инциденты
   Все запросы к модели пишутся в журнал с привязкой к сотруднику и выгружаются в систему мониторинга ИБ (SIEM). Журнал хранится в контуре банка, срок хранения задаёт ИБ. Если в модель отправили лишнее, сотрудник сообщает в ИБ через канал #ai-incidents в течение 1 рабочего часа. За своевременное сообщение санкций нет. Сокрытие рассматривается как нарушение.

8. Контакты
   Вопросы по инструментам – платформенная команда (#ai-platform). Вопросы по правилам – ИБ (#security). Предложения по изменению политики – технический директор, пересмотр раз в квартал.
```

Важно, чего в политике нет: списка запрещённых задач по типам (это решает лид команды через файл контекста), требований к стилю промптов, обязательной отметки каждой строки кода. Политика на 1 страницу живёт дольше, чем регламент на 20 страниц.

## Чек-лист для ИБ

Это вопросы, на которые нужен ответ до согласования инструмента.

- Обучается ли поставщик на наших данных? Есть ли это в договоре?
- Где физически обрабатываются данные? Соответствует ли это 152-ФЗ и отраслевым требованиям?
- Какой срок хранения запросов у поставщика? Можно ли его сократить до нуля?
- Есть ли журнал действий с привязкой к сотруднику? Экспортируется ли он в нашу систему?
- Как инструмент аутентифицирует пользователей? Интегрируется ли с корпоративным входом?
- Какие права получает агент? Можно ли их ограничить по средам и репозиториям?
- Как инструмент защищён от prompt injection? Какие действия требуют подтверждения?
- Что происходит при потере доступа к поставщику? Есть ли план перехода?
- Какие юридические гарантии даёт поставщик по сгенерированному коду?
- Прошёл ли инструмент оценку уязвимостей и когда это было?

Пример заполненного чек-листа по одному из инструментов, которые рассматривал Даниил. Третья колонка – вердикт ИБ, и именно она определяет, идёт ли инструмент в пилот.

| Вопрос | Ответ поставщика | Вердикт ИБ |
| --- | --- | --- |
| Обучается ли на наших данных? | Нет, зафиксировано в договоре, пункт 7.3 | Принято |
| Где обрабатываются данные? | Модель работает в дата-центре поставщика в России, по договору; данные об использовании уходят поставщику | Принято при условии отключения этой передачи или её прохождения через прокси ИБ |
| Срок хранения запросов | Не хранятся после обработки, это зафиксировано в договоре | Принято |
| Журнал действий с привязкой к сотруднику | Да, экспорт в формате JSON по API | Принято, нужна интеграция с SIEM (системой сбора и анализа событий безопасности) до старта |
| Аутентификация | Единый вход (SSO, single sign-on) по протоколу SAML (стандарт, по которому системы передают друг другу данные о входе пользователя), поддерживается | Принято |
| Права агента | Ограничиваются на уровне репозиториев и сред через конфигурацию | Принято, продуктивные среды исключить |
| Защита от prompt injection | Фильтр входящего контента и список действий с подтверждением | Частично: список подтверждаемых действий расширить по политике банка |
| Потеря доступа к поставщику | Инструмент перестаёт работать, пока доступ не восстановят | Принято, план перехода на открытую модель в контуре банка – в течение квартала |
| Юридические гарантии по коду | Возмещение по претензиям о нарушении авторских прав в пределах стоимости договора | Передано юристам |

## Дизайн пилота

- **Цель:** 1–2, сформулированные через метрики из таблицы [блока 11](11-metriki-dora-baseline.md).
- **Baseline:** значения этих метрик за 3 месяца до старта.
- **Группа:** состав по правилам [блока 13](13-komanda-roli-obuchenie.md) (энтузиасты, средние инженеры, скептик, представитель ИБ).
- **Сервис:** типичный, даже если есть более удобный.
- **Задачи:** с чего начинаем (понимание кода, документация, тесты; миграции в корпорации – во второй волне) и что не трогаем.
- **Инструмент:** один, согласованный с ИБ.
- **Бюджет:** лимит на пилот с предохранителем.
- **Срок:** минимум 6 недель данных.
- **Метрики еженедельно:** 5 показателей на одной панели.
- **Как отделим эффект ИИ:** контрольная группа, разнесение по времени или разбивка по этапам ([блок 11](11-metriki-dora-baseline.md)).
- **Критерии успеха:** что должно произойти, чтобы перейти ко второй волне.
- **Критерии остановки:** что должно произойти, чтобы пилот прекратить.

Заполненный дизайн пилота с числами и календарь первых 2 недель есть в [блоке 14](14-pilot-90-dney.md), состав группы – в [блоке 13](13-komanda-roli-obuchenie.md).

Скопируйте промпт в модель, которую разрешила ваша служба ИБ (ChatGPT, Claude, GigaChat, YandexGPT или другую). Модель задаст вопросы по одному и по ответам соберёт документ. Не вставляйте в ответы секреты, персональные данные и код из закрытых систем.

```

Масштабирование:
```
